# Architecture Review and Refactoring Log

## Scope
Review covers the Java demo under `NETFLIX/`: movie catalog, user/profile state, playback, downloads, recommendations, subscription/payment simulation, reviews, analytics, demo entry point, regression tests, and repository hygiene.

## Current design
- **Entry point:** `NETFLIX_DEMO` is a scripted showcase organized into feature-focused methods. It is not an interactive menu.
- **Movie entity and compatibility:** `Movies` represents a movie and preserves legacy static catalog APIs.
- **Catalog service:** `MovieCatalog` owns the in-memory catalog and the search, filtering, ranking, and sorting operations. `Movies` delegates its static query methods to this service.
- **User state:** `NETFLIX_USER` owns profile settings, favorites, watchlist, history, progress, and related state.
- **Feature services:** subscription/payment, playlist, playback queue/session, watch party, download manager, recommendation engine, review, and analytics classes separate feature concerns.
- **Persistence:** data is in-memory only. Arrays and explicit counts are retained for the OOP assignment.

## Findings and fixes

### Repository hygiene — fixed
Tracked generated bytecode was removed. CI compiles the sources and cleans generated `.class` files.

### Watch-party lifecycle — fixed
Ended parties reject chat, invitations, playback seeking, and synchronization. Restart resets to paused at position zero and clears stale mute state. Regression tests cover the lifecycle boundaries.

### Catalog responsibility — refactored
Catalog add/remove/lookup/count/clear and query/filter/ranking/sorting operations now live in `MovieCatalog`. The `Movies` static API remains as a compatibility facade to avoid breaking assignment-facing code. Movie metadata is still part of the `Movies` entity and catalog storage remains static; those are possible future steps, not required for this incremental migration.

### Demo orchestration — refactored
The large scripted demo now calls small feature-focused methods for setup, user/library, subscription, settings, catalog, recommendations, session, watch party, downloads/queue, and analytics. No interactive menu was introduced because the original program is a scripted showcase.

### Smoke tests — refactored
The entry-point runner delegates to:
- `CatalogSmokeTests`
- `PlaybackSmokeTests`
- `BillingSmokeTests`
- `UserFeatureSmokeTests`

`SmokeTestSupport` contains the shared assertion helper. Coverage now includes catalog query migration, locale-independent search, overflow boundaries, playback recovery, payment/refund consistency, expiry validation/masking, user-history transitions, recommendation safety, playlist cursor behavior, watch-party lifecycle, and system-health status.

### Validation/state audit — fixes applied
- Reject non-finite movie/user ratings and recommendation configuration values.
- Saturate cumulative movie watch-time and system-health uptime/counters instead of overflowing.
- Use `Locale.ROOT` for keyword matching.
- Validate payment expiry dates against the current year/month and retain masked card data only.
- Keep wallet default-method selection consistent.
- Preserve state atomically when completing a movie would overflow watch history.
- Harden download storage accounting, playback-queue recovery, playlist cursor movement, promo redemption, invoice/refund state, and watch-party lifecycle; regression tests cover the major boundaries.

## Remaining risks / roadmap
1. **Static/global catalog state:** isolate catalog instances or introduce an interface only if the assignment allows the API change.
2. **Arrays/fixed capacities:** consider `ArrayList` or `LinkedHashSet` behind APIs; preserve capacity limits and legacy array-returning methods where needed.
3. **Console UI:** an interactive menu and input-validation layer are separate optional work. The current entry point remains deterministic showcase code.
4. **Test depth:** smoke tests are useful but are not a full unit-test framework. Continue adding per-class edge-case and state-transition tests.
5. **Naming/API modernization:** add conventionally named aliases only when compatibility constraints are clear; avoid disruptive renames.
6. **Persistence/integrations:** outside this educational simulation's scope unless requested.
